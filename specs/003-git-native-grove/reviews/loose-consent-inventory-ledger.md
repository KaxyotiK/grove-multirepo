**Authority:** constitution 6.0.0 Principle IV; FR-023, FR-023A; `cli-surface-v3.md` recorded consent; V3DES-09, V3DES-10. **Base:** `f143968ccb37a54493b8df9f472f90ae42a42b3d`. **Source:** release item 13 and assessment-18 §8d.

At the base, `delete --allow-destructive-all` recorded loose consent as the top-level names that `unaccountedEntries` returns. Both the direct removal and the resumed `directory-remove` step compared names only, then removed the whole Grove directory recursively. A file added inside a consented loose directory after the plan was therefore inside the consent and was deleted, and the receipt named only the directory.

**Red.** Before any product edit, `tests/cli/loose-consent-inventory.test.ts` ran against a build of the unmodified base: 6 tests, 0 pass, 6 fail; the red run log was kept outside the repository. The three safety witnesses failed because the file was deleted at exit 0: direct (`new.txt` gone), resumed (`new.txt` gone, receipt `recordedLoose: ["notes"]`) and the pre-inventory record (`notes/old.txt` gone). The three controls completed or refused as before and failed only on the directory-level itemization (`["notes"]`). The bound witness and module tests exercise new functions and were added after the red run.

**Design.** `inventoryLooseContent` walks native byte names with `lstat`. It keeps the structural rule of `unaccountedEntries`, lists every loose path with its type, records a symlink as one entry, and does not descend into a directory that carries a Git marker or bare-repository entries. Unreadable content, those Git-owned directories, and the bounds (10,000 entries, 64 levels) make the inventory incomplete. Delete refuses an incomplete inventory before recording a plan, after the nested-Git guard, so an owned checkout is still named as such. The `directory-remove` step records `looseInventory: {version: 1, entries}` and no longer writes `discardedLoose`. An older build (f143968 or 94cf746) that resumes a new record therefore finds no consented names and refuses loose content outside the removed Tree paths. It still deletes content recreated at a removed Tree's path, which it treats as exempt; it does the same with its own records, so that downgrade hazard predates this branch (independent review F5, case a7). At the point of use the Trees are already removed, so anything at a Tree path is inventoried as new content. A recorded entry covers only its own path and type. The inventory records path and type only and does not fingerprint file contents. Receipts and refusals list every path, directories with a trailing `/`.

**Callers of `unaccountedEntries`.** Delete (direct refusal itemization, consent and point of use) and the resumed `directory-remove` now use the per-path inventory. Archive (`archive-content`), rename (`move-content`) and their resumed `directory-move` and `directory-merge` steps (`assertPlannedLoose`, `assertRecordedLooseMove`) keep the name-level comparison. They move the Grove directory, so content added below a name moves with it and is preserved, not deleted.
