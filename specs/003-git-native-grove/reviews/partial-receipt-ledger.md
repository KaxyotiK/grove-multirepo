# Receipts for partial destruction: evidence ledger

**Authority:** constitution 6.0.0 Principle IV ruling ④ ("afterwards what they did lose"); FR-023A; `json-results-v1.md` and `cli-surface-v3.md` receipts; V3DES-11, V3DES-12. **Base:** merge `bc1f4803c3365bfff92f208641b7a94035b6c6ac` (round-one `e6d29ae` with release `94cf746`). **Source:** assessment-18 §8c and its s8 partial-receipt control.

At the base, a forced `archive` or `delete` that failed after an earlier Tree removal returned only the failing target. The completed `worktree-remove` step recorded `{registered: false, refsRetained: true}`, and the files it destroyed appeared nowhere. A failure of the `delete` metadata step after the loose removal produced an error envelope with no receipt at all. On resume, `reconcile` reported only the steps that run completed, so removals by the interrupted run were never reported.

**Receipt shape.** A completed Tree removal's `postState` is `{path, registered: false, refsRetained: true, recordedWork, discardedWork}`. `recordedWork` is the consented set and `discardedWork` is the point-of-use set Git then removed, one `{status, path}` entry per file; a file that vanished before that check is absent. The completed loose removal's `postState` is `{present: false, recordedLoose, discardedLoose}`. A partial `archive` or `delete` result lists each completed step as a target with `reason: null` and that `postState` as `after`, beside the failing target. `archive` also lists its completed content move. Targets not yet attempted are not listed. A failure of the metadata step after destruction is now a partial result with `detail.why` and `detail.remedy`, not an error envelope, and the step stays `recoverable-intermediate`. `reconcile`'s `after.discarded` lists every completed `worktree-remove` and `directory-remove` step, with `completedEarlier: true` for steps completed before this run, `tree` for a Tree removal, and `discardsUnrecorded: true` for a step whose record carries no per-file receipt.

**Success-path changes.** `delete` and `archive` success results are unchanged, except that a `delete` whose content directory was already absent reports `discardedLoose: []`, not the consented list. The operation record's completed steps gain the receipt fields above. A successful resume's `after.discarded` now includes steps completed before the interruption.

**Not covered.** A `git worktree remove` that fails after deleting some files reports that target as failed, with no discards claimed. The contracts now state this (review F2); behavior is unchanged.
